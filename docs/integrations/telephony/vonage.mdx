## Overview

Vonage (formerly Nexmo) is a native Dograh telephony provider. Dograh talks to the
Vonage Voice API directly — there is no intermediary platform:

```
Dograh ──POST /v1/calls (RS256 JWT)──▶ Vonage ──PSTN──▶ callee
Vonage ──signed Answer URL──▶ Dograh  ──NCCO "connect" websocket──▶ Vonage
Vonage ══ signed WebSocket, 16 kHz L16 audio ══ Dograh AI pipeline (STT → LLM → TTS)
Vonage ──signed Event URL──▶ Dograh (call lifecycle)
```

Supported with Vonage:

| Feature | Supported |
| --- | --- |
| Test/single calls, API-triggered calls, campaigns (incl. retries and scheduling) | Yes |
| Organization-default or explicitly selected configuration | Yes |
| Inbound calls | Yes |
| Transfer Call tool | Yes (conversation-based, see [Transfers](#call-transfers)) |
| Answering machine detection | Yes (`machine_detection=continue`, optional) |
| Signed webhooks + authenticated media WebSocket | Yes (required) |
| Audio | 16 kHz 16-bit linear PCM, bidirectional, with barge-in |

## Prerequisites

- A [Vonage account](https://www.vonage.com/communications-apis/)
- A Dograh backend reachable from the internet over HTTPS/WSS (Vonage cannot call `localhost`)
- At least one Vonage virtual number

## Credentials and what they are used for

| Field | Where to find it | Used for |
| --- | --- | --- |
| **Application ID** | Dashboard → Applications | Voice API JWT (`application_id` claim); checked on every signed callback |
| **Private Key** | Downloaded once when you generate keys for the application (`private.key`) | Signing Voice API requests: outbound calls, hangup, transfers |
| **API Key** | Dashboard → API Settings | Identifies your account on signed webhooks; routes inbound calls to the right configuration |
| **API Secret** | Dashboard → API Settings | Only used to point the application's Answer/Event URLs at Dograh when you assign an inbound workflow |
| **Signature Secret** | Dashboard → API Settings → Signed webhooks | Verifying signed webhooks and the media WebSocket handshake (required) |

<Warning>
  Dograh rejects unsigned or invalidly signed Vonage webhooks and media connections.
  A configuration without a valid Signature Secret cannot complete calls.
</Warning>

## Configuration

### Step 1: Create a Vonage Voice application

1. Log in to the [Vonage Dashboard](https://dashboard.nexmo.com/)
2. Go to **Applications** → **Create a new application** and give it a name
3. Click **Generate public and private key**. Your browser downloads `private.key` —
   keep it; Vonage does not show it again
4. Enable the **Voice** capability. You can enter placeholder Answer/Event URLs for now —
   Dograh sets them for you (see [Inbound](#inbound-calling-setup)). If you set them by hand:
   - Answer URL: `https://<your-backend-domain>/api/v1/telephony/inbound/run`, method `POST`
   - Event URL: `https://<your-backend-domain>/api/v1/telephony/vonage/events`, method `POST`
5. Save, then copy the **Application ID** (a UUID such as `aaaaaaaa-bbbb-cccc-dddd-0123456789ab`)

### Step 2: Enable signed webhooks and copy API credentials

1. Go to **API Settings**
2. Copy the **API Key** and **API Secret**
3. Under **Signed webhooks**, make sure the signature method is **HMAC SHA-256 / JWT (HS256)**
   and copy the **Signature Secret**. Signed callbacks are enabled on the application
   automatically when Dograh configures it

### Step 3: Link your numbers to the application

1. Go to **Numbers** → **Your Numbers**
2. For each number, set **Voice** → application to the application from Step 1
3. Outbound caller IDs must be numbers owned by the same account (Vonage rejects
   others with a `403`, which Dograh reports as `number_not_authorized`)

### Step 4: Create the Vonage configuration in Dograh

1. Open **Telephony configurations** (`/telephony-configurations`) → **Add configuration**
2. Choose **Vonage** and give the configuration a name
3. Fill in Application ID, Private Key, API Key, API Secret and Signature Secret.
   Paste the whole `private.key` file into **Private Key**, including the
   `-----BEGIN PRIVATE KEY-----` / `-----END PRIVATE KEY-----` lines. Windows line
   endings, `\n`-escaped keys and keys whose line breaks were collapsed into spaces are
   repaired automatically; the key is validated (it must be an unencrypted RSA key)
   before it is saved
4. Optionally enable **Answering Machine Detection**
5. Optionally toggle **Set as default for outbound calls**
6. Click **Create**

After saving, secrets are never sent back to the browser — the form shows masked values.
Leaving a masked value untouched keeps the stored secret; type a new value to replace it.

### Step 5: Add phone numbers

1. Open the configuration you just created
2. In **Phone numbers**, add each Vonage number in E.164 format, e.g. `+14155551234`
3. Mark one as the **default caller ID** if you want outbound calls to always use it

Dograh stores numbers in E.164 and converts them to Vonage's format (digits without `+`)
only when talking to Vonage. A bare 10-digit number is treated as US/Canada; anything
else must include the country code.

### Step 6: Test an outbound call

1. Open a workflow and click **Call** (or use the API / a campaign)
2. If the org has several telephony configurations, pick the Vonage one
3. Answer the phone — the agent should greet you within a second or two

To make Vonage the organization default, click **Set as default** on the configuration.
Campaigns use the configuration selected at creation (or the org default at that time)
for every call **and every retry**.

## Inbound calling setup

Vonage routes inbound calls per **application**, not per number: one Answer URL serves
every number linked to the application. Dograh points that Answer URL at its
workflow-agnostic dispatcher, then picks the agent from the called number's
**Inbound workflow** assignment.

1. Make sure the number is linked to the application (Step 3 above)
2. In Dograh, open the Vonage configuration → **Phone numbers** → edit the number →
   choose an **Inbound workflow** → Save

On save, Dograh updates the application with:

- Answer URL `https://<your-backend-domain>/api/v1/telephony/inbound/run` (`POST`)
- Event URL `https://<your-backend-domain>/api/v1/telephony/vonage/events` (`POST`)
- Signed callbacks enabled

This update is idempotent: if several Dograh configurations (or numbers) share one
Vonage application, Dograh does not rewrite it once it already points at Dograh.
Removing an inbound workflow from a number **never clears** the application's Answer
URL — doing so would break every other number on the application. Calls to numbers
without an inbound workflow are answered with a short message and hung up.

<Note>
  If Dograh shows a sync warning when you save the inbound workflow, check the API Key,
  API Secret and Application ID (they must belong to the same Vonage account), then
  save again. You can also set the URLs by hand as in Step 1.
</Note>

**Test an inbound call:** call the number from another phone. The configured agent
should answer. Each inbound call creates a run tagged with the configuration and
called number.

Inbound requests are matched to a configuration by the `api_key` claim of Vonage's
signed JWT **and** the called number, then verified with that configuration's
Signature Secret. One organization's Vonage account can never reach another
organization's numbers or workflows.

## Media and audio

The NCCO Dograh returns connects the call to a WebSocket:

- `content-type: audio/l16;rate=16000` — 16-bit little-endian linear PCM at 16 kHz in
  both directions, sent as binary 20 ms (640-byte) frames. The pipeline also runs at
  16 kHz, so there is no resampling and no μ-law conversion
- Barge-in: when the caller interrupts, Dograh sends `{"action": "clear"}` to flush
  Vonage's playback buffer
- DTMF arrives as `websocket:dtmf` events

### WebSocket authentication

The media WebSocket is authenticated twice before the run starts:

1. The NCCO sets `"authorization": {"type": "vonage"}`, so Vonage signs the WebSocket
   handshake with your Signature Secret. Dograh verifies the JWT (issuer, `api_key`,
   `application_id`, freshness) using the run's own configuration
2. The NCCO `headers` carry a per-run HMAC token bound to the organization, workflow,
   run and telephony configuration. Vonage echoes it in the first `websocket:connected`
   message and Dograh checks it

A client that merely knows the WebSocket URL is rejected with close code `4401`, and
the run stays available for the real Vonage connection.

## Call lifecycle

Vonage events are verified, deduplicated and normalized:

| Vonage `status` | Dograh status |
| --- | --- |
| `started` | `initiated` |
| `ringing` | `ringing` |
| `answered` | `answered` |
| `completed`, `complete`, `disconnected` | `completed` |
| `busy` | `busy` (campaign retry) |
| `timeout`, `unanswered` | `no-answer` (campaign retry) |
| `rejected`, `failed` | `failed` (or `busy` / `no-answer` when Vonage's `detail` says `declined` / `unavailable`) |
| `cancelled` | `canceled` |
| `human`, `machine` | not a lifecycle state; stored as `answered_by` (AMD) |

Only events for the run's own call leg move its state; events from the media WebSocket
leg are ignored. Once a terminal status is processed, late or repeated events are
logged but cannot overwrite it or re-trigger retries. The Vonage call UUID is stored
on the run (`call_id` / `call_uuid`) and appears in every Vonage log line together with
the organization, configuration, workflow, run and campaign IDs.

## Call transfers

The agent's standard **Transfer Call** tool works on Vonage calls:

1. Dograh dials the destination (`POST /v1/calls`) with an NCCO that joins a named
   conversation (`transfer-<caller call UUID>`). Vonage stops ringing after the tool's
   timeout (`ringing_timer`, 1–120 s) while the caller hears hold music
2. Destination events arrive at `/api/v1/telephony/vonage/transfer-events/{transfer_id}`:
   - `answered` → Dograh moves the caller into the same conversation
     (`PUT /v1/calls/{uuid}` `action: transfer`) and the AI leaves the call
   - `busy`, `timeout`, `unanswered`, `rejected`, `failed`, `cancelled` → the agent is told
     the transfer failed (`busy`, `no_answer`, `call_failed`) and the conversation continues
3. Cleanup: both legs join with `endOnExit`, so when either party hangs up the other
   leg ends too. If the tool times out, the caller hangs up while the destination is
   ringing, or the caller can no longer be moved, Dograh hangs up the destination leg.

Transfers are cold (the AI drops off once the destination answers); this matches how
transfers behave on the other providers.

## Answering machine detection

When **Answering Machine Detection** is on, outbound calls are created with
`machine_detection: "continue"`. Vonage keeps the call up and reports `human` or
`machine` on the event webhook; Dograh stores it on the run as `answered_by`
(`machine_beep_start` etc. when Vonage includes a `sub_state`). Vonage may bill AMD
separately.

## Error handling

Vonage API failures are classified instead of being reported as a generic failure:
`invalid_credentials`, `malformed_private_key`, `invalid_application_id`,
`number_not_authorized`, `invalid_number`, `destination_rejected`,
`insufficient_balance`, `rate_limited`, `provider_unavailable`, `network_timeout`.
Rate limits (HTTP 429) and connection errors are retried up to three times. Call creation
is never retried after a 5xx or timeout, because Vonage may already have placed the call.
Error messages never contain keys, secrets or tokens.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Outbound call fails with invalid_credentials (Vonage 401)">
    - The private key must belong to the configured Application ID. Regenerating keys in the dashboard invalidates the old `private.key`
    - Paste the full key including the BEGIN/END lines
  </Accordion>

  <Accordion title="Outbound call fails with number_not_authorized (Vonage 403)">
    - The caller ID must be a number owned by the same Vonage account
    - Check the number in Dograh is entered correctly in E.164 format
  </Accordion>

  <Accordion title="Call connects but there is silence, or it drops right after answering">
    This is almost always the media WebSocket:
    - Your backend must be reachable over `wss://` from the internet; check proxies/load balancers allow WebSocket upgrades and don't idle-timeout long calls
    - Look for `media websocket rejected` in the API logs:
      - `handshake not signed by Vonage` → the Signature Secret in Dograh doesn't match the account's, or the API Key/Application ID differ from the account that owns the application
      - `run token mismatch` → the NCCO was produced by a different configuration than the run uses; recreate the call
      - `no websocket:connected` → something between Vonage and Dograh is stripping the WebSocket's first message
    - Check the Vonage Voice Inspector for `websocket` leg errors
  </Accordion>

  <Accordion title="Signed webhook validation failed (401 from Dograh)">
    - The Signature Secret in Dograh must match Dashboard → API Settings
    - The signature method must be HS256 (JWT)
    - The host clock must be accurate: callbacks older than 5 minutes are rejected as replays
    - The application must belong to the API Key saved in Dograh
  </Accordion>

  <Accordion title="Inbound call gives busy tone and Dograh shows no logs">
    - Confirm the number is linked to the Vonage application configured in Dograh
    - Confirm the application's Answer URL is `https://<your-backend-domain>/api/v1/telephony/inbound/run` with method `POST`
    - Confirm your backend domain is public
  </Accordion>

  <Accordion title="Inbound call plays an error message and hangs up">
    - The called number must exist in the Vonage configuration in Dograh and have an **Inbound workflow** assigned
    - The webhook's `api_key` must match the configuration's API Key
  </Accordion>

  <Accordion title="Transfer always fails">
    - The transfer destination must be a valid E.164 number
    - Check the transfer leg in the Vonage Voice Inspector; the destination's caller ID is one of the configuration's numbers
  </Accordion>
</AccordionGroup>

## Cost considerations

Vonage bills per minute, per number, and for optional features such as AMD. The Voice
API reports call price in the account's billing currency. See
[Vonage pricing](https://www.vonage.com/communications-apis/voice/pricing/).
